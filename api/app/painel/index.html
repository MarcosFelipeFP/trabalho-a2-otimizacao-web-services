Uma API de biblioteca, medida de verdade

Cada botão deste painel chama a API REST e mostra o que ela devolve nos cabeçalhos: quantos comandos SQL a requisição executou, quanto tempo ficou no banco e se a resposta veio do cache. A barra no rodapé mostra cada chamada HTTP, com o método, a rota, o status e esses cabeçalhos.

Item 1 · seção 3 do enunciado

Cache da ficha do livro

Problema
A ficha do livro custa 3 consultas. Com o banco a ~155 ms, cada leitura leva quase meio segundo.
Alternativa
Guardar a ficha no Redis (cache-aside) por 600 s. Alterar o livro pela API apaga a ficha depois do commit.
Evidência
X-Cache, X-Consultas-SQL e o horário em que a ficha foi montada.

Experimento obrigatório da seção 3.4

Os cinco passos do enunciado, com o livro acima. Cada passo é marcado quando a resposta da API mostra o comportamento esperado.

  1. 1
    Consultar e registrar o comportamento do cache Com o cache vazio, “Ler com cache”: MISS, 3 consultas.
  2. 2
    Repetir a consulta: houve reaproveitamento? “Ler com cache” de novo: HIT, nenhuma consulta, a mesma ficha.
  3. 3
    Modificar a informação por uma operação da aplicação “Alterar pela API (PUT)”: a API apaga a ficha do cache.
  4. 4
    Consultar de novo: a informação veio atualizada? “Ler com cache”: MISS, já com o título novo.
  5. 5
    Demonstrar a expiração (TTL) e o risco do dado desatualizado Com a ficha no cache, altere por fora da API e leia com cache: HIT com o título antigo. Encurte o TTL e, quando ele acabar, leia de novo: MISS com o título do banco.

E se o Redis cair?

O cache é um atalho, não a fonte dos dados. Se o Redis não responder em 0,5 s, a ficha vem do banco (X-Cache: INDISPONIVEL) e a requisição não falha. Até o Redis voltar, a API nem tenta usá-lo: uma vigia o testa a cada segundo. Uma alteração feita nesse intervalo deixa a invalidação pendente, e a vigia a faz antes de o cache voltar a ser usado.

  1. 1
    Ler com o Redis fora do ar Com o Redis travado, “Ler com cache”: 200, com a ficha vinda do banco (INDISPONIVEL).
  2. 2
    Alterar com o Redis fora do ar “Alterar pela API (PUT)”: a alteração vale e a invalidação fica pendente.
  3. 3
    O Redis de volta: a ficha antiga não volta Quando o Redis voltar, “Ler com cache”: MISS com o título novo, e não HIT com o antigo.

O que não vai para o cache

A disponibilidade muda a cada empréstimo e devolução. Um valor guardado deixaria emprestar um livro que já saiu, por isso ela é sempre lida do banco (seção 3.1: volatilidade e consequências do dado desatualizado).

Item 2 · seção 4 do enunciado

LAZY, EAGER e a consulta otimizada

Problema
A página de empréstimos mostra o título do livro e o nome do leitor. Com LAZY, cada um vira uma consulta a mais: o N+1.
Alternativa
EAGER com JOIN, JOIN FETCH na consulta e a projeção, que traz só as 8 colunas usadas. SQL nativo para comparar.
Evidência
Consultas SQL por requisição, tempo no banco e bytes lidos do banco. As sete devolvem o mesmo JSON.
O LAZY com 20 empréstimos leva uns 7 s: são 41 viagens até o banco.

    Item 2 · seção 5 do enunciado

    Índice no histórico do leitor

    Problema
    O histórico filtra 300 mil empréstimos por leitor_id, faz JOIN com o livro e ordena por data. Sem índice, o banco lê a tabela inteira.
    Alternativa
    CREATE INDEX idx_emprestimo_leitor_data ON emprestimo (leitor_id, data_emprestimo DESC)
    Evidência
    EXPLAIN ANALYZE: tipo de varredura, linhas examinadas, blocos lidos, ordenação e tempo de execução.

    Índices da tabela emprestimo agora: —

    Sem o índice

    Rode o EXPLAIN ANALYZE sem o índice criado.

    Com o índice

    Crie o índice e rode o EXPLAIN ANALYZE de novo.

    O custo de manter o índice

    Espaço e escrita (seção 5.4). Todo INSERT em emprestimo atualiza cada índice da tabela. Medido com 20.000 empréstimos inseridos numa transação desfeita no fim (README, seção 4.5):

    Índices extras em emprestimoTamanho dos índicesInserir 20.000Por linha
    nenhum (só a chave primária e livro_id)8,9 MB851 ms42,5 µs
    (leitor_id, data_emprestimo DESC)17,9 MB1.224 ms61,2 µs +44%
    os três índices do experimento20,1 MB1.693 ms84,6 µs +99%

    Por isso indexar todas as colunas consultadas não compensa: cada índice só ajuda as consultas que filtram ou ordenam pelas colunas dele, e todos encarecem as escritas.

    Em volume: muitos leitores

    O EXPLAIN ANALYZE do histórico de muitos leitores diferentes, sem e com o índice (o painel cria e remove o índice sozinho). A soma do tempo de execução mostra quanto trabalho o banco faz em cada caso: é esse trabalho que, sob carga, limita a vazão.

      Conclusões
      
    
        
      
      • Cache: o maior ganho, porque elimina as viagens ao banco, mas só no acerto. Com o cache frio o
        ganho foi pequeno, e o preço é aceitar dados desatualizados por até um TTL. A ficha vai para o cache; a
        disponibilidade, não.
        • 
      
      • LAZY × EAGER: o N+1 transformou uma página de 20 empréstimos em 41 consultas. Declarar EAGER
        não diz quantas consultas serão feitas: joined fez 1, selectinload 3 e
        immediateload 41.
        • 
      
      • Projeção: 178 colunas para usar 8. A otimizada leu 28 vezes menos dados e gastou metade da CPU
        da API. Sob carga, a vazão quase empatou com a do EAGER até 50 VUs, porque o gargalo era a viagem, mas a cauda não:
        p95 de 843 contra 1.100 ms; com 200 VUs, 75 contra 62 req/s. O SQL nativo não trouxe ganho sobre ela e custa
        manutenção e portabilidade.
        • 
      
      • Índice: quase não muda uma consulta isolada, mas tirou o banco da saturação: o dobro da vazão com
        50 VUs. Cada índice extra encarece as escritas.
        • 
    
      
    
      
      
      Como demonstrar, por meio de evidências, que uma mudança realmente melhorou o desempenho?
        Medindo as versões no mesmo ambiente, com as mesmas cargas, aquecimento e repetições; olhando os percentis, porque a
        média esconde a cauda; acompanhando consultas, CPU e banco, e não só o tempo; e explicando o mecanismo por trás de
        cada número.
